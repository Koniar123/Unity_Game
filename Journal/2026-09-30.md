# Development Journal — Player Combat, Enemy Attack Animation & Cleanup

**Time Spent:** ~3 hours

## Overview

Today I continued working on the combat system.

The main focus was creating a separate `PlayerCombat` system for blocking, connecting the player's blocking state with the enemy hitbox, setting up the enemy attack animation with Animation Events, and cleaning up parts of the existing combat code.

## What I Implemented

### PlayerCombat

I created a new `PlayerCombat.cs` component.

The script uses the existing `PlayerInputActions` and handles the player's Block action separately from `PlayerMovement`.

The current blocking logic uses:

```text
Block.IsPressed()
```

and exposes the current state through:

```text
IsBlocking
```

This gives other systems a way to check whether the player is currently blocking.

### PlayerMovement Cleanup

I started moving the blocking responsibility out of `PlayerMovement`.

`PlayerMovement` now gets a reference to `PlayerCombat` and can use:

```text
PlayerCombat.IsBlocking
```

for movement restrictions.

This is used for conditions such as preventing sprinting and jumping while blocking.

The goal is to keep the actual combat input inside `PlayerCombat` instead of having it directly inside the movement script.

### Enemy Attack Animation

I continued setting up the enemy attack animation.

The enemy uses an `Attack` Animator Trigger to start its attack animation.

The attack is now connected to Animation Events so that the animation can control the timing of the enemy weapon hitbox.

The events used are:

```text
EnableHitbox
DisableHitbox
FinishAttack
```

### EnemyAnimationEvents

Because the enemy Animator is located on the weapon object, I created `EnemyAnimationEvents` on the same object.

The component connects the animation events with the appropriate enemy components.

It forwards:

```text
EnableHitbox()
DisableHitbox()
FinishAttack()
```

to the enemy hitbox and `EnemyAI`.

### EnemyHit

I created `EnemyHit` based on the existing `SwordHit` system.

The component contains an active hitbox window and uses a `HashSet<PlayerHealth>` to prevent the same attack from registering multiple hits against the player.

The enemy weapon now checks for `PlayerHealth` when its hitbox is active.

### Blocking Check

I connected `EnemyHit` with `PlayerCombat`.

When the enemy hitbox detects the player, it retrieves the player's `PlayerCombat` component and checks:

```text
PlayerCombat.IsBlocking
```

If the player is blocking, the hit is registered but normal damage is not applied.

### EnemyAI Cleanup

I cleaned up the enemy attack code by removing the direct damage logic from `EnemyAI`.

The enemy AI is now responsible for starting the attack and controlling the attack state, while the weapon hitbox is responsible for detecting the actual hit.

I also removed the old attack-delay based damage handling from the AI as part of connecting the attack to the animation and hitbox.

## Problems I Encountered

### Animator On The Weapon

The enemy Animator is located on the weapon object instead of the main enemy object.

This meant that the Animation Events needed to be handled from the weapon's GameObject.

I solved this by creating `EnemyAnimationEvents` on the weapon and using it to communicate with `EnemyAI` and `EnemyHit`.


## What I Learned

Today's work helped me understand how to separate combat responsibilities between different Unity components.

I worked with:

* Unity's New Input System
* Component references
* `IsPressed()`
* Animation Events
* Animator Triggers
* Weapon hitboxes
* Parent/child component lookup
* Separating AI logic from damage detection
* Using `HashSet` to prevent duplicate hits

A major part of today's work was connecting the enemy attack animation with the actual weapon hitbox instead of keeping the attack timing entirely inside the AI code.

The combat system is now being split into smaller components with clearer responsibilities, making it easier to continue developing the player and enemy combat systems.
