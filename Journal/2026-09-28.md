# FPS Sword Game — Development Journal

## Project Overview

I am developing a first-person melee combat game in Unity. The main weapon is a sword, and the current goal of the project is to build the core gameplay systems from scratch and understand how they interact with each other.
Instead of putting all the gameplay logic into one script, I am separating the project into smaller systems. At the moment, the main scripts are:

* `PlayerMovement` — player movement, camera, combat input and blocking.
* `PlayerHealth` — player health and death state.
* `EnemyAI` — enemy detection, movement and attacks.
* `EnemyHealth` — enemy health and death.
* `SwordHit` — sword hit detection and damage.

This structure makes each script responsible for a specific part of the game.

---

## Player Movement

The player controller is built using Unity's `CharacterController`.
The player can currently:

* Move using the movement input.
* Look around using the mouse.
* Sprint.
* Jump.
* Fall using custom gravity.
* Block with the sword.

The movement speed can be changed from the Unity Inspector. There are separate values for normal movement and sprinting.
The movement is calculated relative to the player's forward and right directions, which allows the player to move naturally relative to the direction they are looking.
I also added a check to normalize the movement vector when necessary. This prevents diagonal movement from being faster than moving in a single direction.

### Jumping and Gravity

The player uses custom gravity instead of relying on a Rigidbody.
When the `CharacterController` detects that the player is grounded, the vertical velocity is reset to a small negative value. When the jump input is pressed, the vertical velocity is calculated from the jump height and gravity.
When the player is in the air, gravity continuously decreases the vertical velocity.
This gives me direct control over how jumping and falling feel.

---

## Camera and Head Bob

The first-person camera is controlled separately from the player's horizontal rotation.
Horizontal mouse movement rotates the player around the Y axis, while vertical mouse movement controls the camera's X rotation.
The vertical rotation is clamped between `-90` and `90` degrees so the player cannot rotate the camera completely upside down.
I also added a head-bobbing system.
When the player is moving, the camera moves slightly using sine and cosine calculations. Sprinting uses different bob speed and intensity values.
When the player stops moving, the camera smoothly returns to its original position.
This is intended to make movement feel less static and more like a first-person game.

## Player Combat

The player can attack using the sword.
The attack is controlled through Unity's Input System and has an attack cooldown.
When the player presses the attack button:

1. The script checks whether the player is currently blocking.
2. It checks whether the attack cooldown has finished.
3. If the attack is allowed, the attack timer is updated.
4. The Animator receives the `Attack` trigger.
5. The attack animation is played.

The cooldown prevents the attack from being triggered repeatedly every frame.
Blocking works in a similar way. The `isBlocking` value is updated based on the block input and is sent to the Animator using:

```csharp
animator.SetBool("Block", isBlocking);
```

While blocking, the player cannot attack and cannot sprint.

## Sword Hit Detection

The actual sword damage is handled separately in the `SwordHit` script.
The sword uses a trigger collider to detect when it hits an enemy.
However, the hitbox is not active all the time. It can be enabled and disabled using:

```csharp
EnableHitbox()
DisableHitbox()
```

This allows the sword to deal damage only during the correct part of the attack.
The sword currently deals:

25 damage

The damage value is configurable from the Inspector.

### Preventing Multiple Hits

One problem with trigger-based melee combat is that a sword could potentially detect the same enemy multiple times during one swing.
To prevent this, I use:

```csharp
HashSet<EnemyHealth> hitEnemies
```

When an enemy is hit, it is added to the HashSet.
If the same enemy enters the trigger again during the same attack, the script checks:

```csharp
if (hitEnemies.Contains(enemy))
    return;
```

and ignores the additional collision.
The HashSet is cleared when a new attack hitbox is enabled.
This means that one sword swing can damage an enemy once, while a new swing can damage the same enemy again.

## Player Health
The player has a separate `PlayerHealth` component.
The player has a configurable maximum health value, currently set to:

100 HP

At the start of the game, the current health is set to the maximum health.
When the player receives damage, the health is reduced and then clamped to zero using:

```csharp
currentHealth = Mathf.Max(currentHealth, 0f);
```

This prevents the health value from becoming negative.
The player also has an `isDead` boolean.
When health reaches zero, the player is marked as dead and the `Die()` method is called.
Other scripts can access this state through:

```csharp
public bool IsDead => isDead;
```

This allows the enemy AI to know whether the player is still alive.

## Enemy AI

The enemy currently has a basic AI system based on the player's distance.
When the enemy starts, it searches for a GameObject with the `Player` tag.
It then gets:

* The player's `Transform`.
* The player's `PlayerHealth` component.

The enemy has configurable detection and attack ranges.
Current values are:

Detection Range: 10
Attack Range: 2
Move Speed: 2
Rotation Speed: 5
Attack Cooldown: 1.5


Every frame, the enemy checks whether it should continue operating.
It first checks:

```csharp
if (player == null)
    return;

if (playerHealth == null)
    return;

if (playerHealth.IsDead)
    return;
```

This prevents the AI from trying to interact with a missing or dead player.

---

## Enemy Detection and Chasing

The enemy calculates the direction from itself to the player:

```csharp
Vector3 direction = player.position - transform.position;
```

The Y value is then set to zero because the current AI is intended to move horizontally.
The distance to the player is calculated from the direction vector.
The AI then has three basic states:

Player outside detection range
        ↓
       Do nothing

Player detected but outside attack range
        ↓
      Chase player

Player inside attack range
        ↓
       Attack

When chasing, the enemy rotates toward the player using `Quaternion.LookRotation` and `Quaternion.Slerp`.
It then moves forward in the direction of the player.
This gives the enemy basic movement and smooth rotation rather than instantly changing its rotation.

---

## Enemy Attack

When the player is close enough, the enemy stops chasing and enters the attack logic.
The enemy first rotates toward the player.
It then checks the attack cooldown:

```csharp
if (Time.time < lastAttackTime + attackCooldown)
    return;
```

If the cooldown has finished, the enemy attacks and calls:

```csharp
playerHealth.TakeDamage(10f);
```

The current enemy attack deals 10 damage.
The cooldown prevents the enemy from damaging the player every frame.

---

## Enemy Health

The enemy has its own `EnemyHealth` component.
The current enemy starts with:

100 HP

When the sword hits the enemy, `SwordHit` calls:

```csharp
enemy.TakeDamage(damage);
```

The enemy health is then reduced.
If the health reaches zero, the `Die()` method is called and the enemy GameObject is destroyed.
The current death system is intentionally simple because I am focusing first on making the underlying health and combat logic work correctly.

---

## Current Enemy Death System
The next improvement is to add an explicit death state to `EnemyHealth`.
Currently, the enemy is destroyed when its health reaches zero, but `EnemyHealth` does not yet store an `isDead` state.
I want to change the system so that the enemy can explicitly know:

Alive → true
Dead  → true

The AI can then check this state and stop operating when the enemy itself is dead.
This keeps the responsibilities separated:

EnemyHealth
    ↓
Health and death state
EnemyAI
    ↓
Movement and behaviour

This is also useful for future features such as death animations, sounds or effects because the enemy does not have to be immediately destroyed.

## Code Structure

One of the main things I am learning from this project is how to divide gameplay logic into separate components.
Currently the structure is:

PlayerMovement
├── Movement
├── Camera
├── Jumping
├── Sprinting
├── Head Bob
├── Attack Input
└── Blocking

PlayerHealth
├── Health
└── Death State

SwordHit
├── Hitbox
├── Enemy Detection
└── Damage

EnemyAI
├── Player Detection
├── Chasing
├── Rotation
└── Attacking

EnemyHealth
├── Health
└── Death

This is helping me understand that a larger game can be built by connecting smaller systems rather than creating one large script responsible for everything.
